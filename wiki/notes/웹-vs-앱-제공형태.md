# 웹 vs 앱 제공 형태

[[평생보장소득]]을 **앱으로 낼지, 웹으로 낼지, 둘 다 낼지.** 팀장이 9/14 "앱이 아니라 확장성 있는 웹으로, 웹 단독 기준으로 검토"를 요청했다.
**아직 결정이 아니다.**

## 팀장 의도 (이강민 해석)
- **접근성.** 앱 설치가 허들이다. 외부로 빠르고 작게 내보내 반응을 본 뒤 결정하는 쪽 (한민우가 물은 두 해석 중 **전자**)
- 앱 하나만이 아니라 **웹·앱 둘 다 있는 상태**를 지향

## 현실 제약
- iOS 개발자가 없다. 모바일 앱은 **안드로이드만** 가능 ([[한민우]]) → 웹이면 iOS도 커버

## 비교 ([[한민우]])
| 축 | 웹 | 앱 |
|---|---|---|
| 접근성·바이럴 | **설치 없이 바로.** 결과 페이지 공유로 "나는 이렇게 나왔는데 너도 해봐" | 설치 허들 |
| 인증 | 브라우저에서 카카오·네이버 인증 후 복귀가 불안정 — 리로드될 때도, 안 될 때도 | **SDK 인증.** 카카오톡·네이버가 깔려 있으면 매우 빠르고 자연스럽다 |
| 푸시 | — | 푸시 안정성 |
| 비동기 대기 | 스크래핑 대기 중 앱 이탈·복귀가 브라우저 back/forward/reload에 휘둘린다 | 특정 케이스에서 **뒤로가기를 막고** 프로세스를 강제할 수 있다 |
| 플랫폼 | iOS·안드로이드 모두 | 안드로이드만 |

## 제안 — 웹 유입 페이지 + 디퍼드 딥링크 ([[한민우]])
```
웹 유입 페이지
  서비스 소개 + 온보딩 일부를 외부 제공
  → 간단 입력 → 연령별 평균 연금액·노후 필요 금액 등 "의미 있는 숫자" 표시
  → "내 준비 상태 점검하기"
      → 디퍼드 딥링크로 앱 설치 페이지
      → 설치 후 웹에서 한 온보딩은 생략, 인증만 하면 메인 진입
```
- [[이강민]]: 바이럴을 고려하면 웹이 적절하다
- 프론트 설계 시 브라우저 back·forward·reload를 감안해야 한다
