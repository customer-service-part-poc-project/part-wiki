## 2. 출시 시점 논의 → [[출시-시점-검토]]
| 입장 | 요지 |
|---|---|
| [[이강민]] 1차안 | **2027년 7월 중순~말 출시.** 구글 트렌드상 연금 키워드는 연초 약간, 4~10월 저조, **11월부터 급상승**해 연초까지 이어진다. 11월(길게 10~12월) 마케팅 집중 → 그 전 8·9·10월 3개월 안정화 + 자연 유입 확보. 내년 초 출시는 사업계획·예산이 없어 불가 |
| 개발 ([[김동준]] 추정) | 일정표의 **개발 4개월은 널널하다.** 기획·설계가 앞에서 확실히 검토되면 코딩은 2달이면 끝. **개발 2~3개월로 줄이고 베타·검증 기간을 늘리자.** 다 만들고 검증하는 느낌이 아니라 첫 스텝 산출물을 먼저 사내에 돌리고 이어서 개발·보완 |
| [[이강민]] | 일정표는 Claude로 뽑은 초안이라 개발 기간이 정확히 잡힌 게 아니다. 외부 **베타 출시는 불필요.** 출시 전 **기능 단위 사내 배포**는 필요할 수 있다. 출시 시점만 정했고 세부 일정은 미검토 — 같이 정리하자. 의견에 따라 당기거나 마케팅 고려해 늦출 수 있다 |
| [[한민우]] | **최대한 빨리 나오는 게 맞다.** 법무 검토가 가장 큰 리스크 — 통과 못 하면 기획이 뒤집힌다 |
| [[이강민]] | 쿠콘도 당장 쓸 수 있어도 **예산이 없으면 계약 못 한다** |

## 3. 변액 일정과 공통 개발 → [[공통-모듈-개발-검토]]
| 항목 | 내용 |
|---|---|
| [[Direct-변액저축보험]] 일정 | **출시 목표 2027년 4월** ("4월 CC"). 개발은 지금부터 — 상품이 없는 상태에서 개발 검수 중. **상품은 2027-01-01 등록** 예정. 그 전엔 다른 변액보험 상품(전사 "시렐리티")을 기준으로 틀부터 |
| 변액과 마이데이터 | 변액저축은 마이데이터를 안 쓴다 |
| 변액과 평생보장소득의 관계 | 변액저축은 다이렉트 플랫폼에서 기본 판매. **평생보장소득 플랫폼이 판매 채널 하나로 추가되는 형태** → 솔루션을 낼 때 상품을 연계해 볼 수 있다 |
| 공통 개발 제안 ([[김동준]] 추정) | 먼저 개발하는 쪽(변액)에서 **회원가입·로그인·인증·마이데이터 연동 같은 공통 부분**을 맞춰 두면 뒤 프로젝트 기간이 준다. 두 번 따로 구현하지 말자. 다음 도메인 프로젝트에도 재사용 |
| 큐브 사례 | 큐브 프로젝트는 **올해까지 플랫폼 형식으로 공통 기능을 선개발**하고, 내년부터 변액·연금 도메인은 그 위에 비즈니스 로직만 얹는 구조로 설계 중. 다만 그 자원을 우리가 당장 쓸 수 있을지는 모름 (영역 문제) |
| [[이강민]] | 큐브보다는 **우리 서비스가 다른 플랫폼·서비스에 접목되기 쉽게** 공통 개발 방안을 고민. 큐브의 절세 로직 같은 모듈을 우리 쪽에 접목할 수도 |
| 액션 | 공통 개발 가능한 도메인(회원 등) 정리. 프론트·네이티브도 같이 검토 |

## 4. 데이터 출처 문서 ([[한민우]]) → [[은퇴설계-데이터-출처]]
- 자산 **카테고리별**로 나누고 → 출처 → 제약 → 절차를 요약. 색상: 금융 마이데이터(빨강), 공공 마이데이터(다른 색), 출처 없음(수동 입력)
- 파트 공유용 간략판. **상세판이 따로 있다** — 추가 전달 예정
- **금융 마이데이터**: 보험업이라 직접 사업자 불가 → 제휴사 필요. 제휴사가 금융 마이데이터와 **국민연금 조회를 겸할 수 있는지는 법적 검토** 필요
- **[[공공-마이데이터]]**: 트라이해볼 만하다. 주택연금·국민연금 정보 등 항목이 많다. 금융+공공 마이데이터만으로 대부분 확보 가능. **관건은 목적** — 보험 심사·보험금 조회 같은 구체 목적이 필요한데 우리는 "솔루션 제안". 제공처 정부24, 승인처 행안부가 인정해 줄지. 승인 후 API 조회 구조로 보임 (아직 출처만 조사)
- **수동 입력 항목**: 퇴직연금 **DB형** (회사 정보를 알 수 없음. DC·IRP와 다름), **전세보증금** (확정일자 정보가 민간에 안 열려 있음)
- [[이강민]]: 통합연금포털도 DB형은 입력받았던 것 같다. UI에서 **근속연수 + 최근 3개월 평균 임금** 입력 → 산식. "HR플러스에는 있나?"([[한민우]]) → "있다"

## 5. 서비스 제공 형태 — 웹 vs 앱 → [[웹-vs-앱-제공형태]]
- [[한민우]]: 팀장 의도가 (a) 외부로 빠르고 작게 프로토타이핑해 반응 보고 결정인지, (b) 웹 선호인지 궁금. [[이강민]]: **전자**. 접근성(앱 설치 허들) 때문. 앱 하나만이 아니라 **둘 다 있는 상태**로
- 현실: iOS 개발자가 없어 모바일은 안드로이드뿐 → 웹이면 커버 가능
- [[한민우]] 제안: **웹 유입 페이지** — 서비스 소개 + 온보딩 일부를 외부 제공 → 간단 입력하면 연령별 평균 연금액·노후 필요 금액 같은 **의미 있는 숫자** 표시 → "내 준비 상태 점검하기" → **디퍼드 딥링크로 앱 설치** → 설치 후 웹 온보딩 생략, 인증만 하면 메인. 결과 공유로 바이럴
- [[이강민]]: 바이럴 고려하면 웹이 적절
- [[한민우]]: 앱의 가치 — 카카오·네이버 **SDK 인증**(이미 설치돼 있으면 빠름), **푸시 안정성**, 스크래핑 **비동기 대기 중 이탈·복귀 제어**(앱은 특정 케이스에서 뒤로가기를 막을 수 있음). 브라우저는 back·forward·reload가 있어 인증 후 복귀 시 리로드 여부가 제각각 → 프론트 설계 시 고려
