# 사실과 계획 분리 원칙

[[평생보장소득]]의 정보구조를 지배하는 설계 원칙.
**3탭 구조가 왜 이렇게 생겼는지를 설명하는 단 하나의 규칙이다.**

## 무엇을 정했나
> **"사실"과 "계획"을 절대 섞지 않는다.**

| 탭 | 성격 | 다루는 것 |
|---|---|---|
| **현재** | 사실 | 마이데이터로 **확인된** 실제 자산만 |
| **플랜** | 조건부 | "이 계획대로라면" — 전부 가정 |
| **마이** | 설정 | 목표, 연동, 설정 |

- 미래를 다루는 요소(소득 계단 그래프 등)는 **현재 탭에 두지 않는다**
- 플랜 탭에서 세운 계획이 실제로 실행되면, **마이데이터를 거쳐서만** 현재 탭에 반영된다
- 사용자 직접 입력 항목은 `확인됨(마이데이터)`과 절대 섞지 않고 `본인 입력(미확인)`으로 구분 표시한다

## 왜
- 계산 결과가 "사실"처럼 보이면 서비스가 책임질 수 없는 숫자를 단정하게 된다.
  마이데이터는 **예상수령액을 주지 않으므로** 미래 금액은 전부 우리 가정이다 → [[마이데이터-연금정보]]
- 가정치는 숨기지 말고 화면에 노출한다는 방침과 짝을 이룬다 ([[김동준]])

## 따라 나오는 결정들

**① 플랜 이행 체크 기능을 넣지 않는다**
월별로 계획을 지켰는지 체크리스트로 추적하지 않는다.
현재 탭이 방문할 때마다 실제 상태를 자동 반영하고 플랜 탭도 열 때마다 재계산되므로,
별도의 이행 체크 플로우가 필요 없다. 정기 요약이 필요하면 현재 탭 인사이트 피드로 흡수한다.

**② 플랜 탭은 상태를 저장하지 않는다**
열 때마다 그 자리에서 재계산한다. 저장되는 상태값이 없다.

**③ "설정하기"는 실행이 아니다**
플랜 탭 추천 모달의 "설정하기" 버튼은 **계획 금액을 수정할 뿐** 가입 완료를 뜻하지 않는다.
- ⚠️ 남은 과제: 카피가 실행 완료로 오인되지 않도록 설계해야 한다 (PRD 오픈 이슈)
